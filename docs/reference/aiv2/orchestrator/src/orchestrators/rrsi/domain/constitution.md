# Constitution for harness edits (hub chat domain)

1. Generality. Every instruction, skill, memory note and setting must make
   sense for an unfamiliar request of the same kind of work. No names,
   entities, file names, numbers or answers taken from the evolve set.
2. Evidence. Every edit targets a failure mode, capability gap or success
   habit reported by the analyst, and cites the tasks it should move.
3. Scope. One edit = one mechanism. Keep the change to the fields of its
   component; do not rewrite unrelated text.
4. Bounded work. Retries, reviews and step budgets must have an explicit
   upper bound. Never make finishing depend on a confirmation that may not
   arrive.
5. Preserve habits. Do not break behaviors listed as success habits.
6. Frozen surface. The policy model, the grader, the tool environment and the
   request set cannot be changed; settings that select a model are refused.
7. Memory is for procedure, not content. Notes may record how to work
   ("verify numeric claims with a tool before stating them"), never what was
   found in a particular request.
